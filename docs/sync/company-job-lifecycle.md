## Functional boundary and decision

An authorized user can delete a company-created Job while offline. Deletion leaves the normal list but retains an accessible history. If another device independently renamed the Job or edited any details field, synchronization preserves the deletion and attributed edits as a visible deletion conflict. An explicit Keep edited Job or Delete Job resolution observes that conflict. Keeping does not resolve separate name/details conflicts. A healthy deleted Job cannot be generally undeleted in this increment.

Use a finite Job lifecycle graph, not `jobs.deletedAt`, a newest-clock winner, or another generic sync framework. Current create validation binds the complete immutable Job row. Names and details already have independent causal reducers; retain them and their signed bytes.

Compare the alternatives before implementation: full child-aware lifecycle would require child materialization, baseline authority and exchange that do not exist in the current company sync; transporting legacy line operations alone would not create those missing prerequisites. The selected medium-sized vertical slice handles the currently supported company-created, child-free Jobs. It does not complete all of #63 or #61.

## Authenticated child-free profile

Lifecycle authoring and incoming admission require the exact supported fresh genesis profile: verified company/shop/root/facts binding, authority version1, empty signed entity bindings, compatible protected security floors, and the immutable create operation's facts commitment equal to that protected genesis. Check zero child rows and associated baseline/operation/receipt history under the top-level write lock, and recheck at final protected commit. Centralize this rule at the trusted boundary. Unexpected child data refuses without mutation or an applied ACK; do not discard it.

This is stronger than local absence. Fresh bootstrap issues authority1 and empty entities. Recovery always increments authority and can emit empty entities despite old bindings, so recovered authority, nonempty legacy entities and unknown profiles are unsupported. Current legacy business writes refuse company stores, and typed line writes require a signed entity/baseline binding matching current facts, including inside their transaction. Members cannot issue those line assertions. No supported writer can create a valid child in this admitted profile. Tests must pin those claims. A later child feature must version this profile and its lifecycle rules before enabling children.

Unsupported new lifecycle commands show a specific unavailable reason. Existing data and tombstones remain retained. If current authority cannot verify a history, show unavailable/needs attention, never an empty or live Job. Do not weaken revocation or historical receipt checks to make recovery appear supported. No authority-chain infrastructure, child cascade/exchange, business restore bypass or compaction is included.

## Named data and causal rules

`JobOperationRef` is a typed reference to a name, details or lifecycle signed payload digest within one company/shop/Job/creation. Use compact canonical tagged strings on the wire. `JobCausalContext` is a sorted unique frontier of those references. Resolve every reference to verified original signed history and its typed receipt. Reject foreign scope, wrong family, duplicate/self references, missing dependencies and unsupported versions.

`SetJobLifecycle` binds scope, Job/request ID, immutable creation digest, a captured `JobCausalContext`, choice `deleted|kept`, and explicit resolution intent. Wire contract `job.lifecycle.set@1`. `kept` requires a real explicit conflict resolution. The derived `CompanyJobLifecycleView` has live, deleted or deleteConflict states, original attributed alternatives and the captured context. Add it to `CompanyJobView`; do not rewrite the base Job or old operations. Usage is `commands.setJobLifecycle(command, ownerSession: owner)` with context captured from the verified displayed view.

Deletion observes all known metadata/lifecycle graph heads. A covered earlier edit does not revive the Job. A concurrent edit produces a visible deletion conflict in either arrival order. A local resolution must match the captured current displayed frontier; never silently refresh it. An incoming valid resolution concurrent with an unseen edit retains that edit as an alternative.

Name/details commands add nullable `observedLifecycleHeads`: null preserves historical v1 encoding; an explicit list, including empty, produces `job.name.set@2` or `job.details.patch@2`. Preserve existing v1 bytes and receipt verification. Production UI captures explicit lifecycle heads for new edits. New ordinary edits that knowingly observe deletion or an unresolved deletion conflict refuse. A legacy local v1 request cannot newly author past lifecycle history; exact committed retries remain valid. Incoming valid v1 history has no lifecycle observations and cannot supersede a deletion or explicit keep; genuinely concurrent old edits remain visible. A new ordinary edit observing an explicit keep can proceed, while a later concurrent deletion still conflicts. Existing field-parent rules and explicit field-resolution intent remain intact.

Keep every old operation, original author, stable ID and relationship. Exact verified retry returns its original receipt before new frontier/capacity checks, with current required authorization still enforced. Changed content under the same scoped request refuses. No implicit restoration from edits, create replay or settings import.

Incoming validation judges an edit's signed observed lifecycle context, not the receiver's current deleted flag. Otherwise delete-first would reject the valid concurrent edit. Reduce the combined typed graph after admission. Maximal deleted intent competing with a live edit/keep is a deletion conflict. Equal deleted intents retain all operations without inventing disagreement. Maximal live edits/keeps remain live and retain any field conflicts. A keep resolution never erases an unseen field edit. Validate that explicit resolution actually observes a deletion conflict; it cannot serve as an ordinary undelete of a healthy tombstone.
