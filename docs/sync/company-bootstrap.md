## Choice of custody, recovery and session design

| Option | Custody, login and recovery | Judgment |
| --- | --- | --- |
| A. Reuse installation signing seed as company root, hash a short PIN in SQLite, export that seed in backup | Smallest code change, but a copied backup clones installation and authority; legacy PIN and restored DB could impersonate the owner; no independent recovery rotation or protected rollback floor. | Reject: hard safety failure. |
| B. Distinct company authority, registered recovery signing key, and installation signing key; protected local PIN record and in-memory owner session; separately encrypted recovery package; rotate authority on replacement and issue a new installation grant | Uses the current installation/store boundary and job-line verifier. More state transitions, but each identity has one purpose. Recovery carries a checkpoint, never the old installation seed or live session. | **Choose**, subject to measured KDF and security review before enabling. |
| C. Derive the root directly from the owner's everyday PIN on each login | Avoids storing a root seed, but an offline short PIN becomes an authority attack surface and authority cannot be rotated independently from login; recovery and PIN change become coupled. | Reject. |
| D. Pack all bootstrap secrets and counters into the existing 2,048-byte installation record | One CAS is simpler, but the current identity, facts pin, floors and pending-command witness already consume that record; growth or a command could exhaust it and block ordinary recovery. | Reject after measuring headroom; use one deterministic companion and fail closed on cross-record mismatch. |

Data shape for B: immutable random UUIDs for `companyId`, `shopId`, `userId`, `deviceId`, `grantId`, `installationId`, and `installationGeneration`; a company-root Ed25519 key pair; distinct recovery Ed25519 key pair; current installation Ed25519 key already protected by the native installation store; signed canonical `companyFacts@2` in SQLite containing company/shop IDs, explicit policy, root authority generation, the one admin user and device grant, capability and version values, and registered recovery public key plus package ID. The existing protected installation record pins company/root/fact commitment, path/store generation and monotone known floors. One deterministic reserved protected companion namespace (derived from the existing base namespace, **not** user/company text) holds a bounded `companyCustody@1` record: stable company/install IDs and generation, store generation/bootstrap intent witness, root private seed, recovery private seed while initial package export is pending, PIN KDF profile/salt/keyed verifier, attempt budget and package salt/nonce/digest. The companion is keyed to the same stable installation/store/company tuple; a base CAS revision is compared **during each pending transition only**, not stored as a permanent equality condition, because command begin/seal/reconcile legitimately advance it. Every base-record copy constructor must preserve bootstrap status and its stable companion binding. If either record is absent, divergent, replaced or over the native 2,048-byte cap, reconciliation fails closed. The native namespace validator must admit exactly the reserved suffix for `production` and matching synthetic namespaces, never arbitrary company namespaces. `unjoined` has no companion; `pending` retains seeds through restart; `active` keeps only the current root seed and PIN material, and deletes/tombstones the recovery seed after verified export. Reset/restore cannot silently orphan or reuse a companion: company reset already refuses, and partial-bootstrap retry must reconcile it before any new Create. No capacity increase or SQLite plaintext fallback.

The root private seed is callable only through a private typed authority-fact/rotation signer after bootstrap proof; ordinary job-line operations use the distinct installation key through their existing verified path. There is no public arbitrary-bytes root signer, and a live user session never contains the root seed. The encrypted recovery file holds a recovery private seed, the signed checkpoint facts and floor snapshot, package ID, company ID and authority generation; no installation seed, catalog PIN hash, user verifier, or session. The protected bootstrap intent commits to the final ciphertext digest after export; the signed facts cannot contain that digest because the ciphertext itself includes the facts. Signed public facts never contain raw PIN or verifier. A package's passphrase is distinct from the daily PIN and must satisfy a measured offline-attack-resistant policy.

`companyFacts@2` needs an explicit parser and signature domain. Keep strict v1 parsing for existing fixtures and old proofs. The v2 verifier must bind `recovery` and `shop` fields into its canonical commitment and reject unknown security-critical keys. `readCompanyTrust` and both operation/receipt signers must check the separate bootstrap status too; a protected trust pin in `pending` cannot authorize merely because generic installation reconciliation succeeds. A registered recovery key may authorize exactly `authority.rotateForRecovery@1`, not ordinary business operations. Rotation signs old checkpoint hash, new authority public key, new installation ID/generation/public key and grant, retained company/shop/user IDs, new credential version, and componentwise maximum of all trusted known floors. It cannot turn a stale package into proof of unseen changes. On a replacement with no other trusted checkpoint, show the package's generation/date as the last known state; do not claim latest global authority or revocation state. If a local protected floor or another authenticated newer checkpoint exists and exceeds the package, refuse rollback; an irreconcilable fork becomes `needsRecovery`. No automatic joining or trusting a same-name company.

## Activation and recovery protocol

The following is a separate company bootstrap transition layered on the existing installation-binding readiness. A local key being ready is insufficient for company operations.

| State | Durable evidence | Allowed behavior / next transition |
| --- | --- | --- |
| `unjoined` | Valid local installation only; no company pin, fact, or bootstrap intent | Legacy app remains as before. Create is offered only after a read-only empty-shop preflight (no Parts, Jobs, business photos/history, or ambiguous restored identity); nonempty or already enrolled shops refuse before mutation. |
| `pending` | Protected CAS intent pins a single bootstrap ID, generated IDs, key references, package ID and intended fact commitment before SQLite writes; ciphertext digest is pinned later | No company data or assertion signing. Repeated Create with same intent resumes and returns same IDs. A different Create refuses. Write signed facts and one bootstrap witness transactionally, write/verify encrypted recovery package at user-chosen destination, then reread protected key and SQLite facts. Missing/replaced package cannot activate. |
| `active` | Exact install key challenge, installation binding/store path, protected intent/floors, signed fact commitment, PIN record and recovery proof all match | Clear intent via CAS and issue owner login only after PIN verification. `canUseCompanyOperations` is derived from this fresh reconciliation and current company facts, never a freely set flag. Company shell remains locked until login. |
| `needsRecovery` | Any missing protected key, foreign/restored DB, divergent facts, floor rollback, invalid package proof, incomplete uncertain write, or conflicting authority | No company routing, login, assertion issuance, or legacy fallback into that store. Show a recoverable reason without secrets. An exact pending transaction may resume; otherwise require the explicit recovery route. |

Ordering is protected intent and companion seeds/key references -> SQLite signed-facts transaction -> protected ciphertext-digest CAS -> native same-descriptor exclusive creation, bounded write and flush of the chosen destination, then decrypt/signature round trip -> protected activation CAS. Persist the package ID, KDF salt and AEAD nonce in the pending companion before encryption. The user re-enters the passphrase on retry; the same seed, facts, salt and nonce produce the same candidate ciphertext, whose digest must match a previously pinned digest. The native writer creates the chosen destination exclusively and writes through that same handle; it never reopens the path to truncate and never renames over another file. An unrelated existing destination refuses without overwrite, including one created during the digest CAS. A crash during the write can leave an incomplete encrypted output: it remains pending and needs attention, and retry uses a different destination for the same pinned payload; it does not overwrite or delete the partial output. An exact existing destination can resume only after digest and decryption checks. Never store the raw passphrase. At each boundary, inject interruption and cold restart. A crash after SQLite commit but before package confirmation remains pending and reuses the original intent; it does not mint another company. A crash after activation but before UI reply returns the existing active company. SQLite/secure-store writes are not one transaction; each continuation verifies the same IDs and commitments. The recovery package is authority recovery, **not** business-history recovery. If its destination is inaccessible, leave pending or fail before company authority activation. No automatic fallback to a plaintext file or ordinary backup.

Replacement recovery is a distinct, explicit flow: initialize fresh installation ID/generation/key in an empty isolated store; inspect/decrypt the selected package without importing old installation state; validate registered recovery signature and checkpoint; compare every locally known authority, grant, credential, permission and revocation floor; generate a new root and recovery key; sign a recovery rotation with the old registered recovery key; write v2 facts and new grant for the fresh installation; export and verify a new encrypted package before activation; require a new owner PIN and a fresh login. Where the package does not carry later facts, the UI says exactly that and does not assert current global truth. The prior installation is not silently revoked, because an offline new device cannot broadcast that fact; explicit revocation is later enrollment work. Any evidence of a higher known authority or unresolved branch refuses. Never import an old device seed or active session. This is a recoverable **authority** lineage with an empty shop unless separately authorized business-history recovery later exists.

## PIN and live session boundary

Keep `PinService` and `editor_pin_hash` untouched for legacy catalog use. Create a separate company credential service that verifies only the first enrolled admin user against protected local material, with versioned profile ID, random per-user salt, bounded KDF input/output sizes, constant-time comparison and an **eight-attempt protected budget**. Reserve/decrement one attempt by companion CAS **before** each KDF, including parallel or interrupted calls; a failed CAS retries only the reservation, never gives a free guess. Successful verification restores the budget through CAS; a crash before that may consume an attempt but never silently grants access. Increasing delay after failure is bounded; exhaustion locks login until explicit recovery-package authority rotation and fresh PIN setup, not a clock-based reset. No missing-PIN success. A daily PIN and recovery passphrase are different inputs; the recovery key is never derived from the PIN. Candidate KDF is the already cached `cryptography` 2.9.0 `Argon2id` implementation (`C:/Users/weird/AppData/Local/Pub/Cache/hosted/pub.dev/cryptography-2.9.0/lib/src/cryptography/algorithms.dart:470-520`); parameter selection is **not** declared complete. Benchmark **at most two** memory/time profiles with a small bounded sample on actual Windows and Mac release/profile builds, recording hardware/runtime/package version, individual elapsed times and peak-memory observations, without claiming a statistically strong p95. Derive off the UI thread/isolate; reject settings that freeze the UI or exceed the protected-store budget. Do not store the test PIN or derived bytes in results. Start from the library's documented 19 MiB / 2 iterations / parallelism 1 example only as a candidate, then choose a measured versioned profile with a security reviewer. Persist the profile and migration/refusal rules. A short offline PIN still has limited entropy; durable attempt limits and protected custody reduce, but do not erase, the stolen-device threat.

On correct PIN, mint an unforgeable **process-local** `OwnerSession` object bound to company/user/install/grant/credential/permission/fact version, with 15-minute inactivity and 8-hour absolute TTL (reviewable policy constants), tracked using in-process monotonic elapsed time. Sign-out, app background/lock, app restart, company trust change, restore/wipe, or failed reconciliation destroys it. A repeated wrong PIN never extends a session. No session bytes go into SQLite, backups, or the recovery package. UI routes resolve the current session at every entry and on resume; sign-out clears/back-stack replaces the company shell. The existing signed `VerifiedJobLineSession` remains historical command evidence, so local expiry is enforced at **production assertion issuance and local command submission**, not during incoming replay. The issuer constructs the assertion itself from the live session and exact `JobLineCommand.commitment`, current v2 facts and protected floors, signs via the actual installation key, and immediately feeds the existing verifier. Caller-supplied actor, grant, or `signedAssertion` cannot choose the production local author. **In #97**, a production-v2 local `JobLineCommands.patchJobLine` call requires an opaque owner capability, rechecked after taking SQLite's top-level write lock in `_apply` (`job_line_store.dart:284-320`) and again immediately after `beforeCommit` before returning the transaction callback (`:729-732`). Public kernel entry points must not let a signed v2 assertion bypass this live-session gate. Strict v1 fixtures and historical incoming verification remain separate. Session sign-out synchronously blocks new issuance and takes the same in-process command lease: if an issued assertion has not entered the transaction it fails, while an already committing command linearizes before effective sign-out. Incoming `applyIncoming` and historical receipt verification do not need a local login. No fixture-grant import path or public `sign arbitrary bytes` surface.

## Routing and honest product boundary

Create Company is exposed from an unjoined **empty** shop, with explicit `localContinuity` consent, owner PIN setup, recovery passphrase/destination and verification. `boundedAge` is disabled with an explanation. After activation, the first admin can sign in, see immutable company/shop/user/device IDs and local-continuity/recovery status, sign out, and re-enter after cold restart. This is usable account and authority custody, not a fake Jobs migration. While active or locked, a dedicated company shell replaces the legacy `HomeShell`; it does **not** mount legacy Jobs/Catalog/More or inherit their Navigator stack. Current Parts/Jobs editors and MCP are labeled unavailable for company data until their separate authorized migration; do not create a company-looking legacy record. Unjoined preexisting legacy shops keep current routes, catalog PIN, Category > Type > Variant behavior, and backup/copy behavior. Company facts cause current business backup/copy/replacement and wipe preflights to refuse as they do now; show a direct beta warning that the authority package cannot restore shop data. No raw company data is rendered when locked or in `needsRecovery`. Before activation, bump the SQLite schema from 4 to an additive version 5 with a bounded bootstrap witness table and verify the exact a5 **production `AppDatabase` migration** refuses a real schema-5 SQLite file while leaving schema, business data, settings and protected identity unchanged. The current `AppDatabase.onUpgrade` throws on `from > to` (`app_database.dart:99-102`), and Drift 2.31 routes downgrades through that strategy; the old-source test must still prove it. This is source-path downgrade evidence, not an old frozen executable or full UI-startup claim. A new app also checks `user_version` and company marker before routing. A populated legacy schema-4 store may migrate schema safely but remains legacy and is never silently adopted.
