# Restricted company users

[Issue #182](https://github.com/xXKillerNoobYT/Weird-Parts-3rd-run/issues/182) extends the accepted shared-user work in [issue #38](https://github.com/xXKillerNoobYT/Weird-Parts-3rd-run/issues/38), under [issue #33](https://github.com/xXKillerNoobYT/Weird-Parts-3rd-run/issues/33). The current release bound is two additional named Create Job-only users alongside the existing Owner. This increment does not complete Goal 2.

The lock screen selects a stable user ID. User management and provisioning require an explicit target; pending requests retain that ID and their original intent across asynchronous work and retries. Duplicate display names do not identify an account. The authority Owner can create users, replace a selected additional user's PIN and permanently disable that user. An enrolled rootless Owner can receive these changes but cannot issue them. These actions do not replace the Owner's own PIN. Restricted sessions cannot administer users, enroll devices or perform Owner-only Job edits. Existing Parts, Job-line and catalog PIN boundaries remain.

## Protected account collection

Accounts occupy a bounded collection of independent CAS records. The legacy `production.company-user-1` locator and stored account interpretation remain unchanged; `production.company-user-2` adds capacity. Validated synthetic namespaces use the same collection. Locators are local storage addresses, never wire identities. Provisioning the same users in the opposite order on another installation must still route by their signed user IDs.

Each record retains its existing 2048-byte limit, installation/store binding, credential, eight-attempt budget, lifecycle state and transfer receipts. Creating the second user does not rewrite a stable first record. Collection reads may forward-complete an existing durable public-journal intent once; that autonomous recovery preserves every non-journal protected field and the exact previously authorized history. Every occupied locator is validated before the collection is used. Duplicate identities or creation requests, corrupt state and unsupported records fail closed. Disabled users still occupy capacity and cannot be recycled. Raising the release bound later requires matching native namespace contracts and measured acceptance; this change does not admit a third user.

A wrong PIN consumes only the selected user's budget. Successful verification restores that user's budget. Reset, disable, provisioning retry and receipt paths retain the exact user, locator and current account binding; a matching revision in a different locator is insufficient. Creation requests are immutable across the collection. PIN reset and terminal propagation retain their existing root-signed contiguous public history and SQL delivery journals; credentials remain protected and are excluded from business backups. No security floor is lowered.

## Provisioning and policy exchange

Provisioning uses the retained authenticated peer channel, directional KDF purpose, fresh AEAD nonces, signed recipient request and issuance, and encrypted-box commitment. The signed request explicitly negotiates `company.users.collection@1` with capacity two before private credential export. Older or incompatible peers refuse; no dual legacy wire mode or first-user fallback is provided. Existing stored legacy records and receipts retain their interpretation.

`company.job.sync@7` negotiates `company.users.collection@1/job.create.authorization@4`, capacity and a bounded canonical user-ID roster before user policy or Job inventory. Each advertised user completes a signed, explicitly targeted lifecycle exchange before inventory. A genuinely unprovisioned peer may report absence. Absence never deletes known state, recycles an occupied locator or forgets terminal history. Concurrent roster changes require a fresh exchange.

Owner-issued additional-user PIN replacement and permanent disablement propagate independently per user. Public history is durable before replacement private material is accepted. Missing credentials remain unavailable, retries do not refill attempts, and stale material cannot revive a disabled user. The UI distinguishes pending and confirmed delivery. Disconnected installations retain cached rights until authenticated policy arrives.

Create Job authorization retains the original signed user and actual authoring device. Existing sealed Jobs and confirmed receipts remain verifiable after reset or disablement. Unseen work carrying superseded or disabled authority remains held on its authoring installation with original bytes and no applied ACK; eligible Owner work can continue. Held-work resolution is separate.

Existing device sync permits preserve the selected human's permissions and authorship. New-recipient authorization remains authority Owner-only. General roles, additional administrators, unknown-peer introductions, relay/mesh, mobile acceptance and company-backup recovery remain separate work. Source tests, independent review, platform compilation, exact Windows/Mac native acceptance, main integration and post-main verification are separate gates.

## Existing user on an additional installation

The selected-user provisioning command supports an existing Create Job-only user on another directly Owner-enrolled, retained installation. It re-encrypts the existing protected credential. It does not ask for the PIN, change the credential or permission version, rewrite the issuer's original legacy transfer, copy a device key or grant the receiving human administrator rights. A valid restricted A may remain selected while receiving B after explicit per-user consent. Issuance and sender grant completion still require the actual authority Owner.

The `company.user.initial-provision@2` exchange first obtains the recipient's actual receiving-store generation through signed encrypted negotiation. The invitation, logical request, authorization and private issuance bind the selected user, unchanged current public head, source and exact receiving installation/store. A new logical request gets a UUID. Exact retry retains that request through fresh pairing/channel nonces. A peer that does not support this protocol refuses before private export. An established initial-provision recipient does not fall back to the legacy transfer protocol.

The recipient validates the full signed history before admission and stores credentials only in its existing protected user locator. Legacy credential-one users keep protected v2 representation. Current users keep v3 representation and its existing public-journal reconciliation. New installation initializes its own budget once. Retry, or another request for an identical installed credential, cannot refill attempts or rewrite existing protected transfer fields.

The installed-credential ACK uses its own signing domain and purpose-qualified delivery key. It is never placed in protected v3 `r`, whose existing policy-receipt domain remains unchanged. A public policy ACK does not prove credential installation. A receipt for an earlier store is historical until the current receiving binding is authenticated. UI status distinguishes those cases. The sender adds the ordinary recipient-bound credential-update grant only after verifying the installed ACK and rechecking current Owner, target credential, authority and peer state. Old recipient grants remain intact.

Public authorizations and receipts reuse existing schema-14 tables. Logical-request keys exclude mutable target/head/user fields so changed bodies collide rather than evade duplicate detection. Valid legacy grants coexist with the new records; malformed or unsupported authorization records fail closed. Protected credentials, their digests and device private keys are excluded from public proof and business backups.

Interrupted activation is not automatically a fresh account. Complete public-only state may receive its missing credential only with verified protected inbound policy provenance, complete history and current Owner authorization. Ambiguous null/outbound staging refuses direct adoption. The supported authority-Owner Sync flow can complete its existing public state; provisioning may then retry against the exact installed credential. A verified installed newer head and complete signed ancestry may supersede an older pending authorization under fresh Owner intent, preserving the old evidence. Old ACKs cannot confirm a newer credential.

This initial-provision profile bounds history to the origin plus 16 subsequent certificates, at most 128 durable authorization requests per issuer installation/generation, the existing two additional-user locators and 2048 bytes per protected record. Exact retries do not consume another authorization record. Capacity refuses rather than truncating history or deleting evidence. These enforced bounds are separate from measured native capacity and platform acceptance.

The increment addresses direct Owner-to-additional-installation provisioning. It does not introduce unknown peers, delegate enrollment, provide global offline revocation or administrator recovery, or establish three physical devices/mobile/mesh acceptance. An older application reading new public records is a distinct compatibility gate; preserving another old recipient alone does not prove that gate. No native-acceptance or main-delivery result is asserted by this document.
