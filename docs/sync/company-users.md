# One additional restricted company user

This increment belongs to [issue #38](https://github.com/xXKillerNoobYT/Weird-Parts-3rd-run/issues/38) under [issue #33](https://github.com/xXKillerNoobYT/Weird-Parts-3rd-run/issues/33). It supports the existing owner and one additional named user with Create Job permission. It does not complete the full shared-user goal. PIN rotation, disablement, additional administrators, third-device distribution, generalized relay, mobile acceptance and company recovery expansion remain separate work.

The company lock screen selects a stable user ID. The authority owner can create the additional user and explicitly provision it to an already enrolled retained peer. The recipient confirms the named user before offering its signed current installation, generation, key and store binding. Both installations can then sign in offline with the same user PIN. The restricted session has no administrator type and cannot issue the existing owner-only Job edits, enrollment or user-management actions. Parts and Job-line editing retain the company shell's existing unavailable boundary and legacy PIN gate.

The new public certificate is `company.user.authority@1`, signed with the current root key under `wiredpart.company.user.authority@1:`. It binds the company, shop, authority, exact facts commitment, user ID, 64-byte UTF-8 name, fixed credential and permission versions, Create Job capability, original request and issuing owner/device. Existing `rootFacts@2`, device enrollment certificates and first-owner recovery retain their strict interpretation. Create Job authorization v4 combines that unchanged device proof with the independent user certificate and uses `wiredpart.job.create.authorization@3:`. Saved operation, retry, signer and final commit paths retain the selected user and actual device. A retained owner channel may carry such an operation only from that same verified device, with the user proof checked separately.

The additional account is one protected CAS record at `production.company-user-1`, or its validated synthetic companion. The native 2048-byte limit is unchanged. The account contains the complete certificate, local binding, private Argon2id profile/salt/verifier, eight-attempt budget, one immutable transfer identity and its durable receipt. Whole-record worst-case UTF-8 capacity is checked before KDF, signing or mutation. No account SQL journal or business-backup credential copy is used. The signed certificate is the creation audit record. Retry and ACK updates preserve current attempts. Only successful verification of that user's PIN restores its own budget. Corrupt, foreign or old-authority account state stays unavailable and is never silently replaced.

Provisioning uses the retained-peer authenticated channel, a separate directional KDF purpose, fresh AEAD nonces, signed issuance and an encrypted-box commitment. The pending sender identity survives interruption. A fresh authenticated retry regenerates the target offer and ciphertext using that same logical identity. Recipient activation and its semantic receipt share one CAS; a lost write response is read back before reporting success. A lost ACK is regenerated without replacing credentials or refilling attempts. Private codec failures become fixed public refusals.

Job exchange uses the explicit `company.job.sync@5` profile. A constant capability exchange occurs before inventory disclosure. Older profiles refuse and leave operations pending. This is still bounded retained-peer exchange, not mesh. Source tests, widget tests, independent review, configured CI and exact Windows/Mac native acceptance establish separate facts. Opening a PR or passing local tests is not native acceptance or main delivery.
