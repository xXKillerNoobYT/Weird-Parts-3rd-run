# Issue 45 foundation scenario specifications

Status **PROPOSED, NOT_RUN** for every row. There are 105 distinct rows across seven areas, exactly 15 per area. These are specifications for the consolidated 195-scenario plan, not passed acceptance evidence. All companies, people, devices, jobs, records and quantities are fictional. Use isolated synthetic stores and local encounters only. No cloud, router or continuous connection is assumed unless a row explicitly names an existing local LAN.

Common planning references are [foundation issue 33](https://github.com/xXKillerNoobYT/Weird-Parts-3rd-run/issues/33), [baseline local MCP issue 37](https://github.com/xXKillerNoobYT/Weird-Parts-3rd-run/issues/37), [company users/PIN/permissions issue 38](https://github.com/xXKillerNoobYT/Weird-Parts-3rd-run/issues/38), [current Nearby lifecycle gate issue 39](https://github.com/xXKillerNoobYT/Weird-Parts-3rd-run/issues/39), [diagnostics issue 40](https://github.com/xXKillerNoobYT/Weird-Parts-3rd-run/issues/40), and [scenario/design plan issue 45](https://github.com/xXKillerNoobYT/Weird-Parts-3rd-run/issues/45). Linking an issue does not claim its implementation or acceptance. The [foundation plan](foundation-plan.md) separates current source, historical evidence and pending native acceptance. The [architecture comparison](architecture-comparison.md) records the five independent design inputs.

Delivery stages have the following meaning.

- **F0** describes the current one-way/recovery gate and existing boundaries. These rows do not add new prerequisites to the current exact95 three-leg same-page test or mark that test complete. Any expanded recovery test proposal remains a specification, not an automatically broadened native gate.
- **F1** is the next company/user semantic sync foundation, only after issue 39's required gate and implementation ownership are resolved. It includes shared operation validation, company/device/user authorization, causal changes, outbox, incoming receipts, conflicts and compatibility contracts.
- **F2** is Parts/jobs usage migration and complete user-facing integration, then Notebook. Notebook scenarios specify later feature acceptance without promoting Notebook into the current native gate.
- **R** is later roadmap work requiring separate policy, design and platform evidence. Router-free bearers, inventory logistics and embedded AI do not become immediate blockers.
- **MCP staging** keeps issue 37 as baseline. F1 prepares and implements the adapter contract through shared validated operations after issue 39. F2 completes the issue 38-backed sign-in/permission UI and full external-client acceptance. Adapter contract tests can precede complete user UI, but real user/PIN authorization cannot be claimed before issue 38. MCP is not deferred to a future embedded-AI project.

Every executable proof cell names evidence still needed. None was run for this artifact. An old device's partial knowledge must remain visible. Unknown required authorization or envelope behavior rejects before company data disclosure. Unknown domain data may enter bounded custody only when the outer authorization, integrity, scope and custody rules are understood. Stored custody, semantic apply and intended-shop acceptance are distinct states. Stable original operation/entity IDs and original user/device provenance survive every relay. Carrier identity never replaces authorship.

Device private credentials and active sessions never clone through backups or user portability. Company users and their PIN sign-in must work offline on any authorized company device after the required protected authorization state is provisioned. Public profile/role records are separate from a protected company-user authentication realm with versioned provisioning, rotation and revocation. The exact portable verifier or credential mechanism is OPEN and requires security review. Raw PINs never enter shared records, ordinary business payloads, logs or audit. The current local shared catalog PIN remains until issue 38 migration. User sign-in/PIN policy is separate from installation membership and catalog write authorization.

Design-gap warning for integration. Any earlier alternative that excludes all company-user authentication state forever conflicts with the user's portability requirement. Preserve private device-key noncloning and raw-PIN exclusion while designing protected company-user provisioning. Do not silently adopt blanket verifier exclusion as the product contract. The user's permission for public development PINs applies only to isolated on-device test installations. Values are omitted from this document and all shared records. No row instructs an agent to expose or enter production credentials.

Causality and detailed changed fields or content units govern conflict handling. Device clock and arrival order do not choose a winner. Original editing users answer from any authorized company device. While unresolved, authorized readers see both highlighted, attributed versions. Preserve replies and partial agreements. An authorized manager may resolve remaining disagreement under reviewed company policy. No embedded AI, character-level merge algorithm, or automatic intent inference is assumed.

Offline revocation cannot be globally immediate without communication. Freshness, historical-action cutoffs, finite history, tombstone retention, peer retirement and rebaseline policy remain explicit open decisions where needed. Finite retention cannot promise unlimited offline convergence without a rebaseline rule.

## Consolidation limits and next proof

These specifications consolidate distinct pressures from architect A's frozen typed design and the copied independent Mac D/E matrices. Originals remain unchanged. Shared concerns recur across layers only where the observable contract differs, such as a credential's authority, protected user provisioning and restored installation identity. Different transport directions or cosmetic actor changes do not count as new scenarios.

The next small semantic experiment remains isolated stores with supported and unsupported registries, original-byte carriage, original-user provenance, atomic outgoing/incoming evidence, explicit stored/applied/accepted results and negative authorization cases. It starts only under the applicable foundation stage after the current issue 39 gate. Current actual-device evidence is neither replaced nor inferred by this document. Future feature scenarios do not broaden present native acceptance. Questions about company authority, stale credentials, finite history and manager escalation stay policy decisions for the coordinator's integrated plan.
